# フィールド別の抽出規則(クロール対象7フィールド + 条件付きの補充3フィールド)

changes を組み立てるときの単一の規則集。確認できたものだけ・書いてあるものだけを提案する。
共通の考え方: **レビューは出典URLを再取得して値の忠実性を突合する**。出典テキストから読み取れない値は絶対に書かない。

## 共通規則

### 転記の基本

- 値は出典の表記に忠実に。**要約・意訳・省略・別ページからの持ち込みをしない**
- 全角英数字・全角記号・全角スペースは半角に、連続空白は1スペースに整理してよい(格納時に NFKC 正規化されるため)
- 明らかな表記ゆれ・明らかな誤植の「修正」をしない(出典どおり)

### source_url(全変更共通)

- **その情報を実際に確認したページ**のURL(トップページではなく、値が載っていたページ)
- `absent` / `unknown` の主張にも source_url が要る: **載っていそうな場所を確認し終えた最後のページ**(通常はお問い合わせページ。会社概要→お問い合わせの順に見たらお問い合わせ)。確認が複数ページに渡るときは**最も蓋然的な1ページ**を出典にし、他に見たページは note に列挙する(レビューは出典ページの本文で検証するため、根拠が添付されないページを source_url にすると検証不能になる)
- ドメインは原則として対象企業の公式サイト(第三者のまとめ・ポータル・SNSは出典にできない)。グループ会社のドメイン(製品・サービスの公式サイトが別法人ドメインになっている場合)は、対象企業自身のサイトから**同一セクション内に列挙・案内されている**ときに限り出典にできる

### note(全変更共通)

- note は**出典テキストに書かれていることの要約・位置の案内のみ**に使う。出典にない語彙・分類・説明を書かない(値と同じ忠実性が review で突合される)

### status 判断(スカラー型)

- `present` — 値を確認でき、整形規則どおりに転記できる
- `absent` — 載りそうな場所(会社概要・お問い合わせ・フッター・サイトマップ)を確認したがどこにも掲載がない。**「メールまたは電話にて回答」等の回答手段への言及は、その手段の案内(ページ・アドレス)が存在することを意味しない → absent のまま**
- `unknown` — 確認したが値を確定できない(複数候補で代表が定まらない / 画像化・難読化で読めない / ページ間で矛盾する)
- `unresearched` — 使わない(未調査のまま残すなら changes に入れない)

**現在値が入力済みのフィールドに `unknown` / `absent` は提出できない**(サーバーの機械検証で422拒否される)。ページ改修・見落とし・JS描出による「たまたま見つからない」と「本当に消えた」は機械的に区別できないため、値の変更は present での上書きのみ。再クロールで見つからなかったフィールドは changes に入れずに提出すればよい(そのフィールドは何も変わらない)。初期調査(現在値が未調査・不明)での「記載なし=absent」「読めない=unknown」は従来どおり有効。

### ページ種別の読み取り(実サイトで観測された形への対処)

- **テーブルの行が崩れて見えるとき**(ラベルと値が別行になる・セルの折り返しで語が分断される)は、HTML原文を返せる取得手段があれば原文で元の構造を確認してから転記する
- **ナビ・フッターのリンク列挙が本文より長いサイト**(大企業に多い)は、リンク列挙を読み込まず本文の見出しから読む。辿るリンクだけ拾う
- **PDF は fetch 対象外**。会社案内・有価証券報告書が PDF のみで HTML に同等情報がなければ、その情報は提案しない(absent/unknown も作らない)
- **拠点一覧ページ**が地図・JS描画で本文がほぼ空になることがある。電話番号は会社概要・お問い合わせ側で確認する(空のページを absent の根拠にしない)

### リスト型(`industries` / `keywords` / `features`)

- **`present` + 空でない配列 でのみ提案する**。空配列 `[]` も `unknown` / `absent` も使わない(反映側の仕様: リストの非presentは「未調査」に戻るだけ)
- 語が1つも拾えない・判断できないときは、そのフィールドを changes に入れない
- 配列の並びは自由(格納時に正準化される)。重複しない

## links.contact(お問い合わせページURL・string)

| | |
|---|---|
| 探す場所 | ナビ・フッター・本文中の「お問い合わせ」「Contact」リンク |
| 値 | リンク先ページのURL(fetch結果に現れるリンクの絶対URL)。mailto: リンクは対象外 |
| present | 問い合わせ用ページ・フォームが存在する |
| absent | サイト内のどこにも問い合わせページがない(メール直書きのみの案内も absent — それは `contact.email` へ) |

- 問い合わせページが複数ある(一般 / 採用 / 法人向け)ときは**一般用**を採る。採用専用フォームは採らない
- リンクを見つけたページが source_url(リンク先ページそのものではない)

## contact.phone(代表電話・string)

| | |
|---|---|
| 探す場所 | フッター・会社概要テーブル・お問い合わせページの「TEL」「電話」 |
| 値 | 番号本体。整形規則は下 |

**整形規則**: `市外局番-市内局番-加入者番号` のハイフン区切りに整える。

- ラベル(`TEL:` `☎` 等)・装飾・前後の文言を除く。括弧書き `(03) 1234-5678` → `03-1234-5678`
- 国番号表記 `+81-3-...` → 先頭を `0` に戻す(`03-...`)
- 内線番号・担当表記(`内線123` 等)は番号に含めない
- フリーダイヤル(`0120`...)はそのまま(`0120-123-456`)

**候補の選択**(複数あるときはこの順で):
1. 「代表」「大代表」「本社」等の**代表と明示された番号**(「(代表)」括弧書きを含む)
2. 一般窓口(お客様相談センター・お問い合わせセンター等、全製品・全業態を受け付ける番号)— この場合も `present` とし、**窓口名を note に書く**
3. それより下(採らない): 採用専用・部門別・製品別・事業部別の窓口(クラリーノ事業部、IR限定等)**しか存在しない**ときは `absent`(代表電話の掲載なし)— 部門番号を代表として提出しない

**代表が複数並立するとき**(大阪本社・東京本社の両方に「(代表)」が付く等)は `unknown`(代表が1本に定まらない)。

上記の整形規則は共通。

## contact.fax(FAX番号・string)

`contact.phone` と同じ整形規則。「FAX」「Fax」「facsimile」表記を探す。
TELのみの記載でFAX行がないときは `absent`(載りそうな場所を確認した上で)。

## contact.email(メールアドレス・string)

| | |
|---|---|
| 探す場所 | お問い合わせページ・フッター・会社概要のアドレス表記 |
| 値 | アドレス本体(ラベル・前後文言を除く) |

- 複数あるときは代表らしい1つ(優先: `info@` / `contact@` / `<ドメイン>` 直下の一般窓口)。部門別(contact@ / recruit@ 等)しかない場合は一般窓口を採り、採用専用は採らない
- **部門・事業部・IR専用のアドレスしか存在しない**ときは `absent`(一般窓口のメール掲載なし)— 部門アドレスを代表として提出しない
- メールアドレスが画像化・JS難読化されて読み取れない → `unknown`
- サイトのどこにもメールでの案内がない(電話・フォームのみ)→ `absent`

## basics.market(上場市場・string)— クロール対象外

上場市場はクロールで確定できない(上場表記がPDF資料にしかないサイトが多く unknown が量産される — #153)。**EDINETコードリスト×東証data_jの権威ソース取り込み(`exchange_import`)が全社を 東証プライム等/非上場 で確定する**ため、クロールでは読む必要も提案もしない。タスクJSONの crawl_fields にも含まれない。

## industries(業界・string_list・語彙ID)

**提案前に必ず語彙を確認する**: corpdex サイトの業界一覧ページ(`/industries`)をfetchする(サイトURLは MCP サーバーのURLのorigin — SKILL.md §4)。ページのリンク(`/industries/<語彙ID>`)から語彙IDを読む。**語彙ID以外は機械検証で拒否される**(表示名・自分で作った英語IDは不可)。fetchで開けない環境では industries は提案しない。

- 事業内容(会社概要・事業紹介)から最も当てはまる**細語彙**(表示名の粒度が細かい方)を選ぶ。細で表せない場合のみ粗語彙
- 複数の事業体系(例: 製造と小売)は複数IDを並べてよい
- 親の粗語彙を自分で追加しない(サーバーが反映時に自動補完する)
- **顧客・取引先の業種は自社の業界ではない**(「自動車メーカー向け」の部品メーカーの業界は機械製造系)
- どの語彙にも当てはまらない・事業の手がかりがない → 提案しない

## keywords(キーワード・string_list)

検索でヒットさせたい語。**製品・サービス・取扱ジャンルの名称列挙**を抜き出す。

- 対象の「列挙」= 箇条書きリスト・番号付きリスト・「製品ラインナップ」「サービス」「取扱ジャンル」「事業内容」「製品カテゴリ」等の専用見出しの下にあるリスト。**読点(、)区切りの文中の並列は対象外**
- **列挙候補が複数ページにあるとき**(事業領域と製品カテゴリ等)は、**製品・サービスカテゴリの列挙を優先**し、最も網羅的な**1ページだけ**を出典にする(複数ページの併合はしない)
- **採録の単位と除外**(原文にある語でも以下は含めない):
  - 「その他」「各種」「全製品一覧」等の検索語として機能しない項目
  - ナビ項目(ソリューション・導入事例・消耗品・オプション等の周辺リンク)
  - リストマーカー(番号 `1.`・記号)と語尾の助詞的継続表記(「ほか」)
  - **「〇〇の製造」「〇〇の設計・製造」「〇〇の販売」等、名称に業務内容が付いた表記は名称部分(〇〇)だけを採る**(「治具の設計・製造」→「治具」)。「精密板金加工」「訪問看護事業」等の複合語の名称はそのまま
  - 上位語とその下位列挙が同じリストにあるとき、下位の列挙を採る(上位語は重複させるため)
- **上限の目安は10語**。超える候補があるときは**カテゴリの語(製品・サービス・ジャンル)を優先し、異なる事業領域を広く覆うように選ぶ**(1つの領域の細かい語を並べない)。ブランド名・個別製品名はカテゴリの語で埋まらない残り枠に、代表的なものだけ足す(全商品・全ブランドを列挙しない)
- 1項目=1語。訳語・略語・読み仮名を作らない。スラッシュ複合表記(「A / B」)は1項目のまま
- **グループ会社の製品・サービス**は、対象企業のサイトの公式列挙に並んでいれば含めてよい(自社列挙の一部として案内されているため)
- 並びは問わない・重複しない

## features(特徴タグ・string_list)

v1 では**取引先種別タグのみ**を収集する:

- `BtoB` — 顧客が法人・事業者。「法人様向け」「〜メーカー向け」等の明示表現に加え、**事業向け製品・導入事例・法人向け窓口の構成から読み取れる場合も可**(そのときは note に根拠を1行書く)
- `BtoC` — 顧客が個人。「個人のお客様」「利用者様」「〜様のご自宅」等の表現、または**お客様相談室・個人向け製品カテゴリ等の個人向け窓口・品目の存在から読み取れる場合も可**(同様に note に根拠)
- 両方読み取れる場合は両方(`["BtoB","BtoC"]`)

判断例(明示表現がなくても、顧客が一般消費者・事業者のどちらかが**事業の種類から自明**な場合はタグを付けてよい。その場合も note に根拠を1行書く):

- ホテル・外食など一般消費者の利用が自明な業種 → `BtoC`
- 部品製造・業務用システムなど事業者向けが自明な業種 → `BtoB`

明示表現も窓口・品目の構成も事業の種類からの自明性もないときは提案しない(推測でタグを作らない)。

## 条件付き補充フィールド3種(資本金・設立日・代表者 — ADR 0009の例外・ADR 0023/#382)

gBizInfoが空の間だけクロール提案できる3フィールド。**提案条件は共通**: タスクJSONの `supplemental_fields` にそのフィールドがあるときだけ提案する。リストにない(空配列の)タスクでは、会社概要に該当情報が載っていても絶対に提案しない(提出ごと機械検証で拒否される)。リストの内容はサーバーがマスター状態から判定するため、自分で判断しない。

### basics.capital_jpy(資本金・int)

| | |
|---|---|
| 探す場所 | 会社概要・会社情報ページの「資本金」行 |
| 値 | **円単位の整数**に換算する(下表) |
| present | 資本金の記載を数値として確認でき、換算規則で一意に決まるとき |
| unknown | 会社概要を確認したが資本金の記載がない・画像化で読めない・単位が確定できない。**`absent` は使わない**(株式会社に資本金は必ず存在する。「公開していない」と「値がない」は別物 — 上場市場の「推測で非上場を作らない」と同型) |

単位の換算(カンマ・スペースは除去する):

| 出典の表記 | 例 | value |
|---|---|---|
| 万円 | `5,000万円` / `資本金:5,000万円` | `50000000` |
| 百万円 | `3,000百万円` | `3000000000` |
| 千円 | `50,000千円` | `50000000` |
| 円 | `50,000,000円` | `50000000` |

- 複数の数値が並ぶ(資本金+授権資本など)ときは「資本金」ラベルの行・セルの値を採る。どれが資本金か確定できないときは `unknown`
- 出典は値を確認した会社概要ページ。**`unknown` も同じ会社概要ページを source_url にする**(資本金の記載を確認し終えたページ — 記載が「なかったこと」の確認元)。gBizInfo 値との突合・整合はレビュー側の管轄(提出時に比べない)

### basics.founded_on(設立日・部分ISOの3精度)

| | |
|---|---|
| 探す場所 | 会社概要・会社情報・沿革ページの「設立」「創業」行 |
| 値 | **西暦の部分的ISO**: 年のみ `1956` / 年月 `2005-04` / 年月日 `1975-03-01`。**出典に書いていない月日を捏造しない**(「1956年」→ `1956`、「2005年4月」→ `2005-04`) |
| present | 設立(または創業)の日付記載を確認でき、換算規則で一意に決まるとき |
| unknown | 会社概要等を確認したが設立・創業の記載がない・画像化で読めない・複数の年が並んでどれか確定できない。`absent` は使わない(設立日を持たない会社は存在しないため — 資本金と同型) |

- **語の優先順位**: 「**設立**」の記載を優先する。「設立」がなく「**創業**」「創立」の記載があるときはそれを採る(両方あるときは「設立」。「創業」と「設立」が別の年を指す会社は実在する — 沿革としての創業と法人としての設立)
- **和暦は西暦に換算する**(元年も1年として扱う): 明治 `1868`〜、大正 `1912`〜、昭和 `1926`〜、平成 `1989`〜、令和 `2019`〜(例: 昭和50年3月1日 → `1975-03-01`、令和元年 → `2019`)
- 「1975年」のように年だけの記載は **年精度のまま** `1975` と書く(`1975-01-01` にしない)
- 出典は日付を確認したページ。`unknown` も同じページを source_url にする(記載が「なかったこと」の確認元)

### basics.representative(代表者・string)

| | |
|---|---|
| 探す場所 | 会社概要・会社情報ページの「代表者」「代表」「CEO」行 |
| 値 | **役職+氏名**(gBizInfoと同じ形式。例: `代表取締役 山田太郎`) |
| present | 代表者の記載を確認でき、整形規則で一意に決まるとき |
| unknown | 会社概要等を確認したが代表者の記載がない・複数名が並び代表が定まらない・画像化で読めない。`absent` は使わない(代表者を置かない会社は存在しないため — 資本金と同型) |

- **整形は並べ替えと括弧書きの展開のみ**: `山田太郎(代表取締役)` → `代表取締役 山田太郎`、`山田太郎(代表取締役社長)` → `代表取締役社長 山田太郎`。**役職語の読み替え・正規化はしない**(「代表取締役社長」を「代表取締役」にしない等 — 出典にない持ち込みになる)
- 役職の記載がない(氏名のみの)ときは氏名のみを提出する(役職を補わない)
- 代表が複数(共同代表等)で1名に定まらないときは `unknown`。代表取締役と社長が別行に並ぶ等、誰が代表か確定できないときも `unknown`
- 出典は代表者を確認した会社概要ページ。`unknown` も同じページを source_url にする

## よくある罠(チェックリスト)

- 会社概要テーブルの**従業員数・所在地は管理フィールド**(changes に入れない)。**資本金・設立日・代表者はタスクJSONの `supplemental_fields` にあるときだけ**提案可(条件付き補充 — ADR 0023/#382)
- 顧客の業種・対象市場を自社の `industries` にしない
- 「お問い合わせはお電話で」のみ → `links.contact` は `absent`、`contact.phone` は present
- 採用専用の電話・メールを代表として採らない
- 1つの情報を複数ページで確認したら、最も明示的なページ(専用ページ > 概要テーブル > フッター)を出典にする
- ナビとフッターに同じリンクが重複して現れる(線形化の仕様)。辿るのは1回でよい
