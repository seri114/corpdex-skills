# corpdex クロールタスク

クロールタスクを1件実行して、企業サイトの調査結果を提出変更(changes)に組み立てる。
あなたが行うのは **①タスクの取得 ②公式サイトの検索 ③取材(fetch) ④changes の組み立て ⑤提出** の5つだけ。操作は MCP サーバー corpdex のツールと、環境の検索・fetchで行う。

**絶対守則(理由は各節)**

1. **取得マナーは自分で守る**。ページの取得は環境のfetch手段(WebFetch等)で行い、**robots.txt・同一ドメイン3秒以上の間隔・1タスク30URL上限・直列実行**を自分で守る(§3)。取得に成功したURLはすべて記録し、提出時に fetched_urls として提出する — サーバーが件数上限と出典との一致を機械検証し、記録にないURLを出典に書いた提出は拒否される(守則2の裏打ち)
2. **出典に書いてあることだけを提案する**。要約・意訳・類推・別ページからの持ち込みをしない。提出物はレビューで出典URLを再取得して突合される(値が出土しないchangesは棄却される)。
3. **取り込み管理フィールドは原則1つも提案しない**: `name` / `name_reading` / `links.website` / `contact.postal_address` / `basics.founded_on` / `basics.representative` / `basics.employees` / `gbizinfo_industries`(gBizInfoが常に正 — ADR 0009)、`basics.market`(上場市場はEDINET×東証data_jの権威ソース取り込みが全社確定する — #153)。会社概要テーブルやIRページに載っていても changes に入れない(入れると機械検証で提出ごと拒否される)。**例外は資本金(`basics.capital_jpy`)のみ**: タスクJSONの `supplemental_fields` に含まれているときだけ、会社概要の資本金を提案してよい(後述 — ADR 0009の例外。リストにないときは資本金も提案しない)。

## 0. 前提

- MCP サーバー corpdex がクライアントに登録済みで、ツール `task_claim` / `task_submit` / `task_abort` が呼びられる(tasks スコープ)。**ツールがなければ、次の順で接続の復旧を試みる**(何をしているかをユーザーに一言伝えてから進める):
  1. `claude` CLI の有無を確認する(`command -v claude` など)。あれば:
      - `claude mcp add --transport http corpdex https://corpdex.jp/api/mcp` を実行する(登録済みなどの失敗は続行してよい)
      - 「ブラウザが開くので、corpdex の承認画面で『承認して接続』を押してください」と伝えてから `claude mcp login corpdex` を実行する(タイムアウトは5分)。ブラウザが開かなかった場合は表示された URL を開いてもらい、完了に必要ならリダイレクト先 URL の貼り戻しを案内する
      - 完了後 §1 の `task_claim` に進む。ツールがまだ呼べなければ「接続は完了しています。このセッションを一度終了し、もう一度クロールを依頼してください(再承認は不要です)」と案内して終了する
  2. `claude` CLI がなければ自動設定はできない。corpdex サイトの協力ページ(https://corpdex.jp/contribute)の案内(コピペプロンプト・クライアント別の設定・PAT での接続)を提示して終了する
- **検索とfetchの手段を持つ**(WebSearch・WebFetch等。なくても§2・§3の代替経路を辿れるが、いずれの手段もない環境はクロール協力の前提を満たさない)
- **1タスクにつき空の作業ディレクトリで実行する**(取得URLの記録と提出物が他タスクと混ざらないようにするため)

## 1. タスクの取得(task_claim)

`task_claim` ツールを引数なしで呼ぶ。

- **`task: null`** なら配布できるタスクなし。その旨を報告して終了する
- タスクJSONが返ったら読むべきもの:
  - `company_name` / `corporate_number` — 調査対象の企業(1タスク=1企業)
  - `priority_fields` — 未調査フィールド(優先して探す)
  - `supplemental_fields` — 条件付き補充フィールド(このリストに `basics.capital_jpy` があるときだけ資本金を提案してよい — 空配列なら資本金は提案しない。リストの内容はサーバーがマスター状態から判定するため、自分で判断しない)
  - `master` — 各フィールドの現在値(全置換の基準。`{status:"unresearched"}` は未調査)
  - `fetch_limit`(=30)・`lease.expires_at`(リース期限)
- **429 quota_exceeded**(同時リース枠・日次クレーム上限)なら、応答の message を報告して終了する

## 2. 公式サイトの検索

**検索手段の梯子**(一次手段が使えない環境がある — 上から順に試す):

1. 環境の WebSearch で `<company_name> 公式サイト` を検索する(同名企業・グループ会社が多い場合は `<company_name> 法人番号` や `<company_name> <事業種> <地域>` を併用)
2. WebSearch がない・結果が不通のときは、**fetch で開ける検索エンジン**で検索する(検索クエリURLをfetchして結果ページを読む。どのエンジンが通るかは環境による — クエリ付きURLを拒否するfetchもある。開ける検索がないなら次の経路へ)
3. 検索で候補が出ないときは、**発見経路を変える**(対象企業のサイトを直接探しても出ない企業が、別の主体を経由すると見つかる — #293):
   - **gBizInfo 法人個別ページの「企業ホームページ」欄**: 住所照合で必ず開くページ(下記)に公式サイトURLの掲載があれば、それを候補にする(掲載のない企業もある — #293 で確認されたのはそちら側)
   - **親会社・グループ公式サイトのグループ企業一覧**: 社名にグループ名を含む等で親会社・グループが推定できるとき、その公式サイトの「グループ企業一覧」「グループ紹介」ページから対象企業の候補サイトを辿る
   - **Wikipedia 記事の外部リンク**: `<company_name> Wikipedia` 等で記事を探し、記事の外部リンクから公式サイト候補を拾う。検索手段が使えないときは `https://ja.wikipedia.org/wiki/<company_name>` の直接fetchでもよい(記事名は裸の社名であることが多い)

いずれの経路で見つけた候補も、採用は通常どおり住所照合で行う。代替経路でのページ取得(グループサイト・Wikipedia を含む)もすべてfetch計数(30上限)に加算される(絶対守則1の適用対象)。経路を辿る分だけ取得は増える(§3 の「通常4〜7回」を超える)ため、上限に余裕を持たせる。

**社名・ドメインが一致して見える候補でも別法人(同名他社)・ドメイン再利用・移転済みの実例が多数ある — 検索1位で社名とドメインが完全一致でも信用しない。公式サイトの確定は、すべてのタスクで住所照合によって行う**(#152):

1. `https://info.gbiz.go.jp/hojin/ichiran?hojinBango=<法人番号>` をfetchして gBizInfo 法人個別ページを開き、**住所**(と代表者名)を控える(社名+法人番号で直接アクセスできる。HTMLなのでfetchで読める)
2. 候補サイトのトップ→会社概要を取得し、**所在地を gBizInfo の住所と照合する**
3. **所在地が一致する候補だけ**を公式サイトとして採用する

住所照合の規則:

- 比較は**都道府県〜市区町村〜町名〜番地**で行う。郵便番号・ビル名・階・「1丁目2番8号/1-2-8」の表記ゆれは無視する
- **代表者名は補助材料**: 一致すれば確定材料になるが、代表変更・商号変更で gBizInfo が旧情報のままの実例があるため、**代表者名の不一致だけでは候補を外さない**(住所で判断する)
- 候補の正式社名が対象企業の**旧社名**でも、住所照合で同一法人なら採用してよい(商号変更)。ただし「〇〇ホールディングス」など親会社・子会社の別法人は、住所が同じ建物でも採用しない
- 候補の会社概要に**法人番号の明示**があれば、番号一致で確定してよい(住所照合に代わる)
- 住所が一致しない・読み取れない候補(画像化・パーキングページ等)は使わない。ドメインや社名の見た目は判断材料にしない

検索結果の候補の選び方(この条件を満たす候補を住所照合にかける):

- ドメインまたはサイト内表記が対象企業と一致(英名・略称・旧社名も可)
- 検索個人ブログ・SNS・ポータルの企業ページは公式サイトではない

コストは gBizInfoページの fetch +1(会社概要は取材で必ず取得するページなので追加ではない)。住所照合を通る候補が1つもない・gBizInfoページ自体が取得できない場合は、**公式サイトを特定できない**とする。**特定できない場合は提出しない** — `task_abort`(reason `site_unidentifiable`)でリースを放棄し、ユーザーに報告して終了する(出典のない提案はできない)。

## 3. 取材(fetch)

- 取得は環境のfetch手段で行う。**絶対守則1のマナーを守る**:
  - **robots.txt**: 2xx で取得できた明示的な Disallow のみ尊重する(robots.txt自体が401/403/5xx・ネットワークエラーのときは「規則不明」として、間隔を守って取得を続けてよい)。robots.txt に Crawl-delay があれば3秒より優先する
  - **同一ドメインは3秒以上あける**(最後の取得から3秒以内の再取得をしない)
  - **1タスクの取得は30URLまで**(URLの重複は除く。gBizInfoページも含む)
  - **直列に取得する**(並行して複数ページを取得しない)
- **取得に成功したURLをその都度記録する**(重複なく)。`task_submit` の fetched_urls として提出する — 出典URLが記録に含まれていない提出は422で拒否される
- 一次のfetch手段が不通のページには、環境にある別の取得手段(ブラウザ・HTTPクライアント等)を併用してよい。すべての手段で不通なら§6へ

**回す順序**(目安。1タスクのfetchは通常4〜7回(gBizInfoページの住所照合+1を含む)):

1. トップページ → 2. 会社概要・会社情報・プロフィール(§2の住所照合はここで確認) → 3. お問い合わせ → 4. 必要なら事業内容・製品・採用
2. 上場市場(basics.market)はクロール対象外(#153 — サイトに上場表記があっても読む必要はない)
3. 途中で新情報が出なくなったら打ち切ってよい(部分提出は正当な提出方法)

**fetch結果の読み方**(markdown化・線形化されたテキストが返る):

- 見出し・リスト・テーブルとして読める。リンクは `リンクテキスト <絶対URL>` の形で現れることが多い(markdown化の形式は環境による — 絶対URLを拾んで次のページに進む)。グローバルナビ・フッター・本文のリンクがすべてここに出る(ヘッダーとフッターで同じリンクが重複して出るのは普通)
- **ナビ・フッターのリンク列挙が本文より長いサイト(大企業に多い)は、列挙を読み込まず本文の見出しから読む**。辿るリンクだけ拾う
- **テーブルの行が崩れて見えるとき**(ラベルと値が別行・セルの折り返しで語が分断)や整形で表記が失われるときは、HTML原文を返せる取得手段があれば原文で構造を確認してから転記する
- **PDF は対象外**。会社案内・有報がPDFのみでHTMLに同等情報がなければ、その情報は提案しない

**サイト内リンクが拾えないとき(JS描出・navと実URLの不一致)は sitemap.xml を読む**:

- `<サイトのルートURL>/sitemap.xml` をfetchする(404なら `/sitemap_index.xml` も試す — 子sitemapのURL一覧が返るので、その中から該当しそうなものをfetchする)
- 一覧から 会社概要・IR・お問い合わせ に当たるURLを選んで fetch する(パスの推測試行による404の無駄打ちを避けられる — fetch計数の節約)
- sitemap も通常のfetchと同じく計数・robots.txt・間隔の対象。URL一覧が長いときは、辿りたいページのURLだけ拾って読み切らない

## 4. changes の組み立て

**組み立ての前に必ず [references/fields.md](references/fields.md) を読む** — 8フィールド+条件付きの資本金、それぞれの抽出規則・整形規則・status判断の定義。初回や判断に迷うときは [references/example.md](references/example.md)(実例: 取材テキスト→提出物)も読む。changes のJSON形状は [schema/submission.schema.json](schema/submission.schema.json)。

要点(詳細は fields.md):

| status | 意味 | 使うとき |
|---|---|---|
| `present` | 値あり | 出典ページで値を確認できた(value に転記) |
| `absent` | 調査したが存在しない | 載りそうな場所(会社概要・お問い合わせ・フッター等)を確認したがどこにもない |
| `unknown` | 調査済み・不明 | 確認したが値を確定できない(複数候補・画像化で読めない・矛盾) |
| `unresearched` | 未調査 | **提出物では使わない**(調査済みなのに未調査は矛盾) |

- **リスト型フィールド(`industries` / `keywords` / `features`)は `present` + 配列でのみ提案**する(空配列・非presentは使わない)
- **資本金(`basics.capital_jpy`)は `supplemental_fields` にあるときだけ提案する**(円単位の整数に換算。「5,000万円」→ `50000000`。会社概要に資本金の記載がなければ `unknown` — 株式会社に資本金は必ず存在するため `absent` にしない。詳細は fields.md)
- `industries` を提案するときは、まず **corpdex サイトの `/industries`(業界一覧ページ)をfetch**し、リンクURL(`/industries/<語彙ID>`)から語彙IDを確認する(**語彙ID以外は機械検証で拒否される**。表示名・自分で作った英語IDは不可)。サイトURLは MCP サーバーのURLのorigin(`/api/mcp` を除いた部分)— 分からなければユーザーに確認する。fetchで開けない環境では `industries` は提案しない
- **触れたフィールドだけを提出してよい**(部分提出)。1つも確認できないフィールドは changes に入れない
- changes は `task_submit` に配列のまま渡す(`company_id` / `fetched_urls` とともに引数で渡す — §5)

## 5. 提出(task_submit)

`task_submit` ツールに渡す引数:

- `company_id` — タスクJSONの `corporate_number`
- `changes` — 組み立てた変更セット(各要素は field / status / value / source_url / note — 形状は schema)
- `fetched_urls` — このタスクで取得に成功したURL一覧(重複なし・30まで。**すべての出典URLを含む必要がある**)

- **422 validation_failed** は機械検証エラー。issues を読んで提出物を直して再提出(サーバーには届いていない)。fetched_urls 関連の指摘は、出典URLが記録漏れ・上限超過のときに出る
- **409 serialized / lease_not_held** はリースの問題(他投稿の確定・リース期限切れ)。`task_claim` からやり直す
- **201** で受理(submission ステータス pending)。成功したらタスク完了。続けてよいかユーザーの指示に従う(次は再び `task_claim` から)

## 6. 中断・失敗(task_abort)

- 何らかの理由でタスクを完了できないとき(サイト消失・時間切れ・ユーザーの中止指示・あらゆる取得手段が不通)は `task_abort` に `corporate_number`(タスクJSONの法人番号)と `reason` を渡してリースを放棄する(放置すると他の協力者が24時間待たされる)。reason は必須で、実態に最も近いものを1つ選ぶ: `fetch_denied`(fetchが403等で拒否)/ `unreachable`(タイムアウト・DNS等で到達不能)/ `site_unidentifiable`(公式サイト候補を特定できない)/ `other`(上記以外)
- fetchがrobots.txt拒否・タイムアウトで続くときは、そのページの情報は諦めて unknown ではなく**提案しない**(出典なき提案はできない)。すべての取材が不能なら abort
- abortした企業は全協力者共通でしばらくタスクに現れなくなる(初回7日・連続で倍増 — ADR 0029)。一時的な障害の可能性が高いとき(ネットワーク断・タイムアウト1回など)は、即 abort せず時間をおいて再試行してから判断する

## クライアント非依存の確認

操作はすべて MCP ツール(`task_claim` / `task_submit` / `task_abort`)・環境の検索・fetch・ファイル読み書きのみで、特定クライアント専用の機能を使わない(MCP に対応する任意のクライアントで同じ手順で動く)。検索もfetchも使えない環境はクロール協力の前提を満たさない。
