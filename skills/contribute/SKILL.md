# corpdex 貢献タスク

corpdex の貢献はクロール(企業サイトの調査と提出)とレビュー(他者の提出の出典突合)の総称で、どちらも同じ貢献ポイントに入る。あなたが行うのは **①キューの確認 ②振り分け ③実行 ④報告** の4つだけ。レビューかクロールかは自分で選ばず、**キュー状況で決まる**。操作は MCP サーバー corpdex のツール(`review_list` / `review_prepare` / `review_approve` / `review_reject` / `task_claim` / `task_submit` / `task_abort`)で行う。

**絶対守則**

1. **レビューを優先する**: 投稿はレビュー2件で着地するためレビューが律速。pending があるときにクロールはしない。**1回の実行は1件だけ**で、実行したら報告して終了する
2. **レビューは出典を自分で取得して突合する**: 突合パケットは変更差分+出典URL一覧+判定基準のみで、出典テキストは同梱されない。パケットの `source_urls` をfetchして、変更値が出典に忠実かを確認する(取得のマナーは crawl スキルの絶対守則1 — robots.txt・同一ドメイン3秒・直列。レビュー1件の取得は数ページだが適用される)
3. 判定・抽出はユーザーの手元の LLM が行う

## 0. 前提

- MCP サーバー corpdex の上記7ツールが呼びられる(tasks・review の両スコープを推奨)。**ツールがなければ、次の順で接続の復旧を試みる**(何をしているかをユーザーに一言伝えてから進める):
  1. `claude` CLI の有無を確認する(`command -v claude` など)。あれば:
      - `claude mcp add --transport http corpdex https://corpdex.jp/api/mcp` を実行する(登録済みなどの失敗は続行してよい)
      - 「ブラウザが開くので、corpdex の承認画面で『承認して接続』を押してください」と伝えてから `claude mcp login corpdex` を実行する(タイムアウトは5分)。ブラウザが開かなかった場合は表示された URL を開いてもらい、完了に必要ならリダイレクト先 URL の貼り戻しを案内する
      - 完了後 `review_list` を呼んで接続を確認する。ツールがまだ呼べなければ「接続は完了しています。このセッションを一度終了し、もう一度『corpdex に貢献して』と伝えてください(再承認は不要です)」と案内して終了する
  2. `claude` CLI がなければ自動設定はできない。corpdex サイトの協力ページ(https://corpdex.jp/contribute)の案内(コピペプロンプト・クライアント別の設定・PAT での接続)を提示して終了する
- レビューにはfetch手段が必要(出典の再取得・突合)。fetch不能な環境はレビュー協力の前提を満たさない
- 空の作業ディレクトリで実行する(取得URLの記録・パケットのメモが他タスクと混ざらないようにするため)

## 1. キューの確認と振り分け(review_list)

`review_list` ツールを呼ぶ(引数なしでpending全体・古い順)。**一覧はあなたが判定を記録できない投稿を最初から含まない**(自分が提出した投稿・自分が既に判定した投稿。運営者トークンは自分の投稿も出る — サーバーが除外するため、自分で判定する必要はない)。

- **`reviews` が1件以上ある** → §2 レビューを1件実行する
- **`reviews` が空(`total: 0`)** → §3 クロールを1件実行する(pending が自分の投稿しかないときもここに来る — レビューできない投稿の突合はせず、新規のクロールに回る)
- **403 insufficient_scope**(review スコープの無いトークン)→ §3 クロールを1件実行する
- **401・接続エラー** → ユーザーに案内して終了する(MCP 接続・スコープの確認)

## 2. レビューを1件実行する

1. `review_list` の**先頭の行**(古い順。`stale: true` は72時間超の滞留)から投稿ID(`s_` で始まる)を取る
2. `review_prepare` に `id` を渡して突合パケットを取得する(状態を変えない操作)。パケットの構成:
   - `criteria` — 判定基準4点(対象企業の確認・提案値の忠実性・status 主張の妥当性・限定解放違反)。判定はこの基準に従う
   - `company` — 対象企業の公表情報(基準1の照合基準値)
   - `changes` — 各変更(field / status / value / source_url / note とマスター現在値 `current`。電話・FAX・メールの現在値は status のみ)
   - `source_urls` — 出典URL一覧(重複なし。レビューアーが取得して突合する)
   - `capital_is_supplemented` が true のとき資本金の現在値はクロール補充の参考値(照合基準から外れる)
3. **`source_urls` をfetchして、各 change の value・status の主張を出典ページと突合する**(公表情報との矛盾は基準1で確認。出典が取得できない change は判定材料がない — 取得を再試行しても不能なら、その旨を comment に添えて reject するかユーザーに確認する)
4. 判定を記録する:
   - 問題ないとき: `review_approve` に `id` を渡す
   - 問題があるとき: `review_reject` に `id` と `comment`(根拠。投稿者に届く却下理由 — 何が悪く何をすべきかを書く)を渡す
5. **403 self_review_forbidden / 409 already_landed / already_reviewed** は、一覧取得後に状態が変わったときのバックストップ。判定を記録せず、リストの次のIDで手順2からやり直す。pending を使い切ったら §3 へ進む

判定に迷うとき・大片の変更のときは、判定根拠を要約してユーザーに確認してから記録する。

**運営者トークン(admin スコープ)の差分**: `review_approve` は1件で確定する(サーバーがトークンの権限で判定)。自分で作った直後の投稿はパケット確認を省略して approve に直行してよい(パケットは他者の投稿や自信のない場合の支援)。

## 3. クロールを1件実行する

crawl スキルの手順に従ってクロールタスクを1件実行する(両スキルは `npx skills add seri114/corpdex-skills -g` で一緒に配置される)。

- `task_claim` が `task: null`(配布できるタスクなし)を返したら、その旨を報告して終了する
- `task_claim` が 403 insufficient_scope(tasks スコープの無いトークン)を返したら、トークンのスコープを案内して終了する

## 4. 報告と継続

実行した内容(レビュー1件 or クロール1件)と結果をユーザーに報告して終了する。**継続を指示されたら §1 からやり直す**(振り分けはその時点のキュー状況で再判定する)。キューも在庫も空になったら「レビュー待ちもタスク在庫もありません」と報告して終了する。

## クライアント非依存の確認

操作はすべて MCP ツール・環境の検索(クロール時のみ)・fetch・ファイル読み書きのみで、特定クライアント専用の機能を使わない(MCP に対応する任意のクライアントで同じ手順で動く)。fetch を使えない環境はレビュー協力の前提を満たさない。§0 の接続復旧は claude CLI がある環境向けのベストエフォートで、なければ協力ページの案内にフォールバックする(操作本体は MCP ツールのみで、この節の規約は変わらない)。
